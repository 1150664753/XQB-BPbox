# 团队资源索引与初始化

## 路径与格式

- 旧索引：`bpbox/profiles/<Profile ID>/manifest.json`。
- 新初始化索引：`.bpbox/profiles/<Profile ID>/manifest.json`。`.bpbox/` 专用于同步元数据，不属于普通素材目录。
- 默认 Profile 的资源仍位于仓库根目录的 `assets/`、`config/`、`results/`；其他 Profile 仍使用 `bpbox/profiles/<Profile ID>/` 下的同名分类目录。
- 历史 `bpbox/profiles/<Profile ID>/blobs/` 与 `previews/` 路径保持兼容，不自动移动或删除。
- 本地同步基线和缓存位于数据根目录的 `.team-sync/<仓库标识摘要>/<Profile ID>.paths-v2.json`，不上传到仓库。

索引沿用 schema 2，并兼容读取 schema 1。顶层含 `schema`、`profileId`、`objects` 和可选 `stores`。每个对象保存稳定 ID、类型、名称、版本、摘要、属性、文件描述和依赖；文件描述包含远程路径、原分类相对路径（旧 blob 可能没有）、SHA-256、大小及扩展名。`stores` 记录共享配置文件摘要。

正常上传按选择构造下一份索引，校验资源及配置后，以原远程 Tree 为基础创建提交，通过非强制分支更新发布。下载依据索引中的路径及摘要取文件，校验后按原目录事务应用；运行比赛时可暂存等待应用。

## 缺失索引的处理

旧实现仅在有历史基线时拦截缺失索引，并把所有失败显示成“远程不可用”；首次连接时则把缺失索引视为有效空索引。现在所有缺失索引都需要手动初始化。GitHub 授权成功只表示已有登录凭据，不代表索引有效或拥有目标仓库写入权限。

界面分别显示空仓库、仓库待初始化、远程索引缺失、索引格式损坏、网络异常、权限不足、仓库/分支无法访问、限流及其他检查失败。已有缓存用于判断此前是否同步；没有历史记录时无法断言索引曾被删除，会明确说明“可能被删除或尚未初始化”。

Contents API 的 404 不能单独证明文件不存在，仍需要同一提交的完整 Git 文件树确认。无提交的空仓库需要 GitHub 明确返回 `Git Repository is empty`，不会根据仓库大小或分支 404 推断。读取失败或文件树不完整时，初始化入口保持关闭。

索引缺失、损坏或远程检查失败时，保留上次索引、基线和本地资源；不生成远程删除操作计划，普通上传/下载均被主进程和界面拦截。此前已经下载并确认的待应用事务沿用原保护机制。

## 使用入口

1. 更新并运行新版 BPbox，进入“团队资源”，确认仓库、分支及 Profile，点击“刷新差异”。
2. 确认索引不存在且 GitHub 返回当前账号具有仓库 push 权限后，点击“初始化远程索引”。权限还受 Contents 授权、组织策略及分支保护限制，实际写入拒绝会显示具体错误。
3. 查看本地对象数量及已有远程文件说明。存在非 Markdown 文件时，需要先备份、人工核对并勾选风险确认。
4. 点击“确认初始化并发布本地资源”。初始化沿用本地扫描、资源过滤、路径规则、配置生成、大小限制、摘要校验和上传进度；视频、缺失文件、外部路径等按既有规则跳过，不可共享属性或无效依赖会阻止初始化。
5. 完成后自动刷新，恢复正常资源对比、上传、下载与缺失资源恢复。

初始化只新增文件或复用完全相同的内容。所有写入路径（包括生成的共享配置、预览图及索引）均检查冲突，不删除或覆盖已有的不同内容。同路径不同内容会停止初始化，风险确认不等于授权覆盖。仅存在于远程的文件会原样保留，但不会自动纳入由本地生成的新索引。

初始化前重新检查索引、写入权限、远程提交和本地快照，避免沿用过期确认。非空仓库的资源和索引在一个提交中发布，非强制更新防止覆盖其他人的并发提交。

无任何提交的空仓库受 GitHub Git Data API 限制，先通过 Contents API 创建唯一的 `.bpbox/initializations/<随机 ID>.md`，再发布完整资源和索引。失败时可能只留下这份说明文件，不会留下有效但不完整的索引；刷新后可重试。若首个提交创建期间仓库已被其他人初始化，将停止并要求重新核对。

## 兼容与维护

新版优先检查独立元数据路径，同时兼容旧索引路径。只存在旧索引时继续在旧位置更新，不自动搬迁；两个位置同时存在索引时停止同步，要求人工核对唯一权威索引，避免双份索引分叉。索引内容损坏也不会被初始化覆盖。

使用新元数据路径的团队应统一更新客户端。旧客户端不识别新路径；不要在新旧客户端之间混用初始化。普通素材清理应只操作 `assets/` 等分类目录，并保留 `.bpbox/`。独立目录不能防止用户手动执行“删除所有非 Markdown 文件”，但此次缺失检测和手动初始化流程可安全处理这种情况。

## 验证

准备上传、生成配置、初始化校验和传输分别上报阶段进度；已知文件总数时显示实际完成数及百分比，扫描期间显示已处理数量和活动指示。网络请求显示等待时间、超时上限与重试状态，整个操作可在提交分支之前取消。

远程缺失文件以同一提交的完整目录树为证据。同一次操作复用已验证的 Git 对象；下次操作重新确认访问权限。不完整递归树仍需核对完整子目录，不会直接视为文件缺失。初始化最终校验复用已核对的资源摘要，避免再次下载相同内容。

`npm run test:team-sync` 包含索引初始化、原有资源同步、GitHub 传输、路径兼容、Electron 和界面交互测试。初始化测试覆盖 Markdown-only、无提交空仓库、删除索引、读写权限、损坏格式、冲突文件及配置、过期确认、提交失败、旧路径兼容、空本地资源和初始化后上传/下载恢复。GitHub 请求通过模拟响应验证，测试不会改动真实资源仓库。
